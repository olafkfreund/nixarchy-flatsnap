# Intent: let the panel's overrides field take a Bus Policy override

## Problem

Line numbers are for `origin/main` at d3a2744.

The panel's overrides field (`Menu.qml:278-287`, `ovField`) is one line of
text bound to `fs.overrides` (`FlatsnapModel.qml:26`). When the user queues a
Flatpak, `queue()` splits that text on any run of whitespace
(`FlatsnapModel.qml:214`, `overrides.trim().split(/\s+/)`). Each token
becomes one `--override` argument (`FlatsnapModel.qml:226`), and the first
Enter's warning is built from the same tokens (`FlatsnapModel.qml:218-223`).

An override's section may contain spaces. The CLI's grammar says so:
`OV_SEC='[A-Za-z][A-Za-z ]{0,40}'` (`bin/nixarchy-flatsnap:20`), and
`cmd_add` matches each `--override` argument against the whole `OV_RE`
(`bin/nixarchy-flatsnap:23`, `:452`). nix-flatpak's own sections
`Session Bus Policy` and `System Bus Policy` contain spaces. So
`Session Bus Policy.org.freedesktop.Flatpak=talk`, typed into the panel,
becomes three tokens: `Session`, `Bus`, `Policy.org.freedesktop.Flatpak=talk`.

What follows:

- The override cannot be entered from the panel at all. The CLI accepts it
  from argv (`nixarchy-flatsnap add flatpak <id> --override "Session Bus
  Policy.org.freedesktop.Flatpak=talk"`).
- It fails safe, but late and unclearly. The first Enter arms and shows
  "change <id>'s sandbox with Session  Bus  Policy.org…=talk". None of the
  tokens matches `_escapes()` (`FlatsnapModel.qml:236-248`), so the red
  ESCAPES wording is not shown. The second Enter runs `add`, and `add` stops
  on `Session` with "override must be Section.key=value" (`:452`). Nothing
  is written.
- Both Bus Policy sections are on the sandbox-escape list added in #12
  (`ESCAPES_JSON`, `bin/nixarchy-flatsnap:38-39`;
  `spec/2026-09-24-12-store-trust.md:102-103`). In the panel, the two rows
  that grant the most are the two it cannot take or warn about.
- The gap is written down in three places as a known hole: the README
  (`README.md:191-193`), the model test (`tests/model.qml:161-163`, no Bus
  Policy case), and the #12 plan's recorded deviation
  (`plan/2026-09-24-12-store-trust.md:158-165`).

The field's placeholder already shows two overrides separated by two spaces
(`Menu.qml:282`), so whitespace as the separator is what users have been
shown since #1.

The Declared list does not show overrides back at all. `cmd_list` emits them
as a JSON object keyed by section (`bin/nixarchy-flatsnap:437`), so a section
with spaces survives there. The row delegate (`Menu.qml:342-354`) prints
store, ID, name, channel, verified and installed, but not overrides. The
field is empty whenever a card opens (`FlatsnapModel.qml:140`) and is not
filled from what is declared. Nothing is parsed back from text, so the
problem is only in the direction from the field to argv.

## Proposed outcome

- Typing `Session Bus Policy.org.freedesktop.Flatpak=talk` (or `own`), or
  `System Bus Policy.<any name>=talk` (or `own`), into the overrides field
  and pressing Enter twice queues the Flatpak with that override. It goes
  as one `--override` argument, and the declared file holds it under the
  section with spaces.
- The first Enter names these two in the red ESCAPES wording, with what they
  grant, as the Context rows already are.
- One field can still hold several overrides, including a mix of Bus Policy
  and Context ones. Each becomes its own `--override`.
- Input the CLI would refuse is still refused, with no partial write.
- The README note (`README.md:191-193`) is gone. `tests/model.qml` has the
  Bus Policy cases that #12 skipped.

## Affected users and systems

- Anyone adding a Flatpak from the panel who needs a D-Bus policy override
  (for example a Flatpak front end or a system-service tool).
- `FlatsnapModel.qml` (`queue()`, maybe `_escapes()`), `Menu.qml` (`ovField`
  placeholder and hint text), `README.md` (Overrides section and keys table),
  `tests/model.qml`.
- `bin/nixarchy-flatsnap`: no change expected. Its grammar is the reference.
- Hosts: the panel runs on any nixarchy host. Live tests go to razer only.
  Nothing is applied, preflighted or run on p620.

## Constraints

- The CLI grammar stays compatible. `add flatpak <id> --override
  Section.key=value …` keeps its argv shape, and `OV_SEC`, `OV_KEY`, `OV_VAL`
  and `OV_RE` (`bin/nixarchy-flatsnap:20-23`) keep matching what they match
  today. Declared files that are valid today stay valid.
- Every override is still validated by the same `OV_*` grammar, in `cmd_add`
  and in `check_entries` for hand edits (`bin/nixarchy-flatsnap:335-337`).
  The panel may check early, but the CLI stays the authority. It must not
  loosen what reaches the file.
- Queuing any override still takes a second Enter, and the ones on
  `ESCAPES_JSON` are still named with what they grant. Editing the field
  after arming still disarms (`FlatsnapModel.qml:30`).
- No shell string building. The panel passes argv arrays to `Process`, one
  element per override, as now (`FlatsnapModel.qml:226`).
- `ESCAPES_JSON` stays the one place the escape list is written.

## Open questions

1. **Which separator should the field use between overrides?**
   - (a) `;`. `OV_VAL` has no `;` (`bin/nixarchy-flatsnap:22`) and neither
     do `OV_SEC` or `OV_KEY`, so it can never be part of an override.
     Unambiguous, but users would need to be told, and it changes what the
     placeholder shows.
   - (b) Newline, with a multi-line field. Unambiguous, but Enter in the
     field is already the first of the two queue presses (`Menu.qml:179-181`),
     so a newline needs another key.
   - (c) Keep whitespace, and split only where the whitespace starts a new
     `Section.key=`. `OV_KEY` and `OV_VAL` have no spaces, so the only
     spaces inside an override are in its section. Note that the lookahead
     split suggested in the issue (`\s+(?=[A-Za-z][A-Za-z ]*\.[A-Za-z0-9_.-]+=)`)
     also matches before `Bus` and before `Policy` inside `Session Bus
     Policy.…`, so it still breaks the section into pieces. It would have
     to be a left-to-right match of whole overrides instead of a split.
   - (d) Recognise only the known section names (`Context`, `Environment`,
     `Session Bus Policy`, `System Bus Policy`, …). Simple, but it is a
     second copy of the section list, and nix-flatpak can add sections.

   *Recommendation:* (c), done as a left-to-right match of whole overrides
   against the same shape as `OV_RE`. It needs no new syntax, the current
   placeholder stays true, and every input that works today tokenises the
   same way. If (c) is judged too clever, (a) is the fallback, and it
   should still accept whitespace when no `;` is present (see question 2).

2. **Must existing input with no spaces inside a section keep working
   unchanged?** For example `Context.filesystems=xdg-pictures:ro
   Environment.LC_ALL=C.UTF-8`, the current placeholder, typed with one or
   more spaces between.

   *Recommendation:* yes. It is the documented form (placeholder, README
   keys table `README.md:56`) and what `tests/model.qml:182` uses. Any new
   rule must give the same tokens for it.

3. **What does the panel do with text it cannot split into valid
   overrides** (for example a stray word)? Today it arms on the first Enter
   and fails in `add` on the second.

   *Recommendation:* say so on the first Enter and do not arm, naming the
   part that does not parse. The CLI still validates on the second Enter.
   This is a small UX change; say if it should wait for its own issue.
