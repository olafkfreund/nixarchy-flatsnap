# Intent: show what a user needs to trust an app before it is queued

## Problem

The app card is where a person decides whether to let an app onto the
machine. Issue #1 promised that the card shows "name, summary, publisher,
license and requested permissions before anything is queued", and that
escalations get "an explicit confirmation step". Today the card hides or
misstates several of the facts that decision rests on. Line numbers are for
origin/main (64f97b2).

1. **Unknown permissions look like no permissions.** `lookup_flatpak`
   (`bin/nixarchy-flatsnap:111`) falls back to `s='{}'` when the Flathub
   summary fetch fails, and the card then says `permissions: none listed`
   (`Menu.qml:201`). A network error makes an app look like the safest
   possible one.
2. **Publisher verification is thrown away.** The publisher shown is a name
   anyone can set.
   - Snap: `lookup_snap` asks for `fields=...,publisher` (`:122`) and gets
     `snap.publisher.validation` back, but keeps only `display-name` (`:130`).
     Live responses: `hello-world` → `{"display-name":"Canonical",
     "username":"canonical","validation":"verified"}`; the first `calculator`
     search hit → `"validation":"unproven"`. Search (`:186`) requests the same
     field and drops it too.
   - Flathub: never asked (`:111-118`). The data exists in two places:
     `GET /api/v2/verification/<id>/status` returns
     `{"verified":true,"method":"website","website":"gnome.org",...}` for
     `org.gnome.Calculator` and `{"verified":false,"method":"none",
     "detail":"Not verified"}` for `com.spotify.Client`; the appstream document
     the plugin already fetches carries the same facts as
     `metadata["flathub::verification::verified"]`, `...::method` and
     `...::website` (null when unverified). The bare path
     `/api/v2/verification/<id>` is a 404.
3. **A snap the store publishes as classic queues on one Enter.** Choosing
   classic yourself takes two presses (`toggleClassic`,
   `FlatsnapModel.qml:143-151`). But when the store publishes the snap as
   classic, `_showCard` (`:114`) or `cycleChannel` (`:136`) sets `classic`,
   and `queue()` (`:170-175`) adds `--classic` with no confirmation. The
   unsandboxed outcome is the same; the warning is weaker.
4. **Sandbox-escaping overrides read like any other override.** `OV_RE`
   (`bin/nixarchy-flatsnap:308`) accepts `Context.filesystems=host`,
   `Context.filesystems=home`, `Context.sockets=system-bus`,
   `Context.devices=all` and
   `Session Bus Policy.org.freedesktop.Flatpak=talk` (which lets the app run
   commands on the host). The second-Enter prompt (`FlatsnapModel.qml:183`)
   echoes the text without saying that these remove the sandbox.
5. **Removing a snap deletes its data, and nothing says so.** The reconciler
   runs `snap remove --purge` (`bin/nixarchy-flatsnap-reconcile:57`) because
   snapd's pre-removal snapshot cannot run on NixOS. The UI confirmation
   (`FlatsnapModel.qml:197`) says only "y removes <id> at the next apply".
6. **Low: no accessibility metadata.** The list rows and the card
   (`Menu.qml:249-271`) set no `Accessible.role` or `Accessible.name`, so a
   screen reader gets nothing from them.

## Proposed outcome

- When the permissions or the verification status could not be fetched, the
  card says **unknown**, in the shell's warning colour, rather than "none
  listed" or nothing. An absent answer never reads as a safe answer.
- The card and the search rows show whether the publisher is verified by the
  store: for Snap from `publisher.validation`, for Flathub from its
  verification data (including the verified domain when there is one).
  Unverified is shown plainly, not hidden.
- Every path that ends in an unsandboxed or sandbox-escaping install asks for
  a second press, whether the user chose it or the store did: store-classic
  snaps, and Flatpak overrides that grant host or home filesystem access, the
  system bus, all devices, or talk to `org.freedesktop.Flatpak`. The prompt
  names what is being given away.
- Removing a snap says, before the confirming key, that its data is deleted
  at the next apply.
- The recorded fixtures and tests cover each case above offline: failed
  summary fetch, verified and unverified publishers on both stores, store
  classic, and each escaping override.

## Affected users and systems

- Anyone installing from the plugin; the people most exposed are those
  pasting an ID from a README who never see the store page.
- `bin/nixarchy-flatsnap`: `lookup_flatpak`, `lookup_snap`, search, the
  override grammar.
- `FlatsnapModel.qml` (`_showCard`, `cycleChannel`, `queue`, `remove`) and
  `Menu.qml` (card and list rows).
- `bin/nixarchy-flatsnap-reconcile`: only its behaviour is surfaced; `--purge`
  itself stays, for the reason in its comment.
- `tests/fixtures/`, `tests/model.sh`, `tests/model.qml`.
- Network: one more read-only request per Flathub card if the verification
  endpoint is used instead of the appstream fields.

## Constraints

- **Store text stays plain text.** Publisher names, verified domains and
  permission strings are untrusted data, rendered as plain text, never markup,
  and never interpolated into a shell string (issue #1's untrusted-input
  constraint).
- **Keyboard only.** Any new confirmation is a key press in the existing
  arm/confirm pattern (`classicArmed`, `overridesArmed`, `disarm()`); no
  mouse, no dialog.
- **Offline tests.** Every new API response is recorded as a fixture under
  `tests/fixtures/` and the tests run without network, as they do today.
- Theme colours come from the shell's tokens (`Color.*`), not literals.
- No change to what is installed or how: this is what the user is shown and
  asked, not the apply path (issue #10) or state handling.

## Open questions

1. Should an unverified publisher need a second Enter to queue, or is showing
   UNVERIFIED on the card enough? Most Flathub apps and many snaps are
   unverified, so a second press on every one may train people to press
   twice without reading.
   *Recommendation:* label only; keep second presses for sandbox escapes.
2. Which override values count as "sandbox escaping" and get the stronger
   warning? Candidates: `filesystems=host`, `host-os`, `host-etc`, `home`
   (and `~`), `sockets=system-bus` / `session-bus`, `devices=all`,
   `Session Bus Policy.org.freedesktop.Flatpak=talk`, any `System Bus Policy`
   `talk`/`own`. A fixed list in the CLI, or everything that widens the
   sandbox?
   *Recommendation:* a fixed, documented list in the CLI, with the ordinary
   override prompt for everything else.
3. Is accessibility (item 6) in scope here, or a separate issue? It touches
   the same QML but is not about trust.
   *Recommendation:* a separate issue, so this one stays reviewable.
