# Intent: the menu's rows, card and confirmations reach a screen reader

## Problem

The flatsnap menu tells a sighted keyboard user everything it needs to, but
none of it is exposed to assistive technology. `Menu.qml` sets no
`Accessible.*` property anywhere (line numbers are for `origin/main` at
c14fdd7):

- **List rows** (`Menu.qml:331-357`). Each row is a `Rectangle` delegate
  wrapping a `Line` whose text is built from the store, ID, name, channel,
  verification and install state. The Rectangle has no role and no name, so
  a screen reader cannot tell a row is a list item or read what it says.
- **Which row is selected** is shown only by colour: the row under the
  cursor gets `Color.menu.selectedBackground` and `selectedText`
  (`Menu.qml:337`, `:341`). Nothing else marks it.
- **The card** (`Menu.qml:239-318`, `cardCol`) is a `Column` of plain
  `Line`s: name, summary, publisher verification, license, permissions or
  confinement, and the classic and AppArmor warnings. It has no grouping and
  no name as a whole, so the trust information on it is not presented as
  one app's details.
- **Confirmations.** Every two-step action arms a state in
  `FlatsnapModel.qml` (`classicArmed` :24, `queueArmed` :29,
  `pendingDelete` :32, `applyArmed` :34) and writes a prompt into
  `fs.message` ("x again: run this snap WITHOUT a sandbox", "Enter again:
  install … WITHOUT a sandbox", "y removes …", the apply summary). The
  footer's message line (`Menu.qml:391-396`) shows it. What marks the line
  as a pending confirmation, rather than an ordinary status such as "nothing
  found", is only its colour: `Color.urgent` while any of the four is armed.
  The line is also never announced when it changes, so a screen reader user
  does not learn that the next key will confirm an unsandboxed install or a
  removal.
- The urgent lines on the card (verification UNKNOWN, permissions UNKNOWN,
  the classic and AppArmor warnings, `Menu.qml:253`, `:266`, `:308`,
  `:314`) carry their meaning in their text, but their urgency is again only
  colour.

These confirmations are the safety gates added in #12 (store trust); a user
who cannot perceive them is the user most likely to press the second key
without meaning to.

Split out of #12 (intent item 6, spec D6). Found in the 2026-09-24
multi-agent review (finding D6).

## Proposed outcome

- With a screen reader running, moving through the list announces each row
  as a list item with the same text a sighted user reads, and which row is
  selected.
- Opening a card announces it as one named group (the app's name and
  store), and its lines, including publisher verification, permissions and
  the warnings, can be read in order.
- When a confirmation is armed (classic, override or classic queue, delete,
  apply), the prompt is announced at the moment it appears, and it is
  identifiable as a confirmation rather than an ordinary status by something
  other than colour.
- A sighted keyboard user sees no difference, unless a non-colour cue for the
  armed state turns out to be needed (see open question 3).

## Affected users and systems

- Users of the flatsnap menu who rely on a screen reader (Orca), or on high
  contrast or no colour perception for the armed state.
- `Menu.qml`. `FlatsnapModel.qml` only if the armed state needs a single
  property the view can bind to (today `Menu.qml:395` ORs the four flags
  itself).
- The flake checks in `flake.nix` (`no-hardcoded-colours`,
  `no-text-multiplier`) must keep passing.
- The sibling nixarchy plugins with similar menus (`nixarchy.pkg`,
  `nixarchy.devenv`, `nixarchy.distrobox`, `nixarchy.podman`,
  `nixarchy.microvm`, `nixarchy.rebuild`) set no `Accessible.*` either (see
  open question 2).
- Test host: razer only.

## Constraints

- No visual change unless one is needed to stop the armed state being
  colour-only.
- The menu stays keyboard only. No new key, and no change to what any
  existing key does.
- Store and build-log text stays plain text (`Line` has
  `textFormat: Text.PlainText`, `Menu.qml:79`). Accessible names are built
  from the same strings and never interpret them as markup.
- Colours stay `Color.*` tokens and font sizes stay `Style.font.*` tokens.
- Nothing is applied or rebuilt on p620. Live checks on razer only.

## Open questions

1. **Can this be verified on this desktop at all?** The AT-SPI bridge is on:
   the running shell has `QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1`, the AT-SPI
   bus is up, Orca is installed, and quickshell 0.3.1 registers on the bus
   (as both `quickshell` and `.quickshell-wrapped_`). But it registers with
   zero children, even while the `omarchy-bar` layer is on screen. So it is
   not known whether a Quickshell `PanelWindow` (a layer-shell surface)
   exposes its item tree to AT-SPI at all. If it does not, `Accessible.*`
   properties would be correct but unreadable by any screen reader here.
   Should the spec start with a probe on razer (open the menu, walk the
   AT-SPI tree, try Orca) before any design? And if the tree is empty,
   do we still add the properties and file the gap upstream, or park #26?
2. **Here, or as a shared pattern?** Of the sibling plugins, only
   `nixarchy.herdr` (`Card.qml:248-250`, `:399-400`) and the non-nixarchy
   `olafkfreund.govee` (`GoveeMenu.qml:233-236`) set `Accessible.role:
   ListItem` and a name. omarchy-shell's own `qs.Ui` components set none.
   Fix flatsnap alone now and copy the pattern later, or agree one pattern
   (for example on `Line`, rows and the message line) and apply it across
   the nixarchy plugins, or ask for it in omarchy-shell's `qs.Ui`?
3. **The non-colour cue for an armed confirmation.** The prompts already say
   "again", "WITHOUT a sandbox" or "y removes", so the text may be enough
   for sight. Is an accessible announcement plus that text sufficient, or
   should the armed message line also change visibly beyond colour (a
   prefix or a marker)? The second is a visual change.
4. **How much of the card to name.** Should the card's group name be only
   the app name and store, with each line read in turn, or should its name
   or description also summarise the trust state (verified or not,
   classic), so it is heard even if the user does not read every line?
