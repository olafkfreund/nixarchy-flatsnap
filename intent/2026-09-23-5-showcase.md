# Intent: show the plugin working, on its own site and on nixarchy's

## Problem

Nobody can see what this plugin looks like before they use it.

- **Its own site** (<https://olafkfreund.github.io/nixarchy-flatsnap/>) has a
  hand-typed text mock of the panel, and no recording.
- **nixarchy's site has nothing about it today.**
  olafkfreund/nixarchy#914 adds a manual page (`manual/flatpak-and-snap`) and a
  section and table row in `manual/plugins`, but both are text only. Every other
  default plugin on that page has a feature GIF and stills: GitHub Actions,
  herdr, MicroVMs, Distrobox, Dev environments. nixarchy's front page and
  README showcase features the same way (`docs/img/features/*.gif`).

The plugin changes what people install and how sandboxed it is. A reader
should see the panel, the permissions card, and the Snap confinement warning
before they press a key, not after.

## Proposed outcome

- **The plugin's site** replaces the text mock with:
  - a recording of the whole flow: paste a Flathub link, see the card, queue,
    apply with the log, the app launching, and removal;
  - stills of the Flathub card with its permissions, the Snap card with the
    confinement warning and the classic confirmation, the Declared list, and
    search results.

  The README carries the recording too.
- **nixarchy's site** showcases it like its other default plugins:
  - a feature GIF on `manual/plugins` (the Flatpak and Snap section) and on
    `manual/flatpak-and-snap`;
  - stills in the same places;
  - the plugin in nixarchy's feature showcase (the front page and README feature
    GIFs), next to Packages.
- All of it follows nixarchy's own media rules, so it reads as the same product.

## Affected users and systems

- **Readers of both sites and both READMEs.**
- **olafkfreund/nixarchy-flatsnap:** `docs/`, `README.md`, and an `img/` directory.
- **olafkfreund/nixarchy:**
  - `docs/img/features/`, `docs/img/plugins/`, `docs/manual/plugins.md`,
    `docs/manual/flatpak-and-snap.md`;
  - the front page and README showcase;
  - possibly `docs/screenshots/`.

  Its CI checks the README counts, the nav, and the plugins-table rows.
- **razer**, the standing test host, where everything is captured. The plugin is
  installed live there, and its desktop is changed and restored.

## Constraints

- **nixarchy's media rules** (`docs/AGENTS.md`), for both sites:
  - a whole desktop at 16:10: feature GIFs at 900x563, stills at 1280x800 or the
    1600x875 set;
  - panels composed onto `docs/screenshots/00-desktop.jpg` (Tokyo Night, Winding
    Road), cut at their own border, with rounded corners and a shadow, centred
    where they really open;
  - GIFs through `tests/demo/encode-gif.sh` (4 fps, 900 px, a palette per GIF,
    96 colours, **under 1 MB**);
  - frames that pass `tests/demo/verify-frames.sh`'s OCR gate (panels at about
    64–80% of the frame).
- **Nothing private on screen.** Panels list real data and translucent windows
  show what is behind them. So capture on an empty workspace on razer, show
  only demo apps (GNOME Calculator, hello-world), declare nothing personal, and
  put the desktop back afterwards: theme, wallpaper, Do Not Disturb, workspaces,
  and the demo apps removed.
- **Shared host.** Announce on the agent bus before driving razer's desktop,
  because another agent records UI tests there with ai-mirror. Post when done,
  with the generation razer is left on.
- **Truthful.** Every capture is the real panel doing the real thing, with no
  mocked text. The current text mock on the plugin site goes away.
- **nixarchy media waits for #914.** The manual page and plugins section it
  illustrates only exist once #914 merges. The nixarchy part is a follow-up PR
  on top of it.

## Open questions

1. **Recording tool.** razer has `gpu-screen-recorder`, not the `wl-screenrec`
   that `docs/AGENTS.md` names. Use gpu-screen-recorder with a 16:10 region
   (then `encode-gif.sh`), or add wl-screenrec to razer for the capture?
   *Recommendation:* gpu-screen-recorder. The encode step is the same, and it
   avoids a razer config change.
2. **Scripted or by hand.** nixarchy's newer GIFs come from `tests/demo`
   scenarios, which are reproducible and re-recordable when the UI changes.
   Write one for this plugin (driving keys with `wtype` on razer), or record a
   single take? *Recommendation:* a small script in this repo
   (`docs/record.sh`), so the next UI change can re-record in minutes.
3. **Front-page placement on nixarchy.** Add a feature tile or GIF next to
   Packages in the front page and README showcase, or keep it to the manual and
   plugins pages? *Recommendation:* next to Packages. It is the second install
   path, and the only one for software nixpkgs does not carry.
4. **Real apply in the recording.** Showing a full rebuild makes the GIF long,
   and apply time is dominated by nixos-rebuild. *Recommendation:* record the
   apply, cut the build log to its first and last lines, and say so in the
   caption.
