# Spec: menu text follows the desktop's scale

## Design

**Decided at intent approval:**

1. Text size is scale-aware: no flat multiplier on top of `Style.font`. Sizes
   come from the shell's `Style`.
2. The menu stays larger than the rest of the shell, but only by a
   scale-aware step: a bigger `Style.font` token, not a multiplier.
3. This repo fixes its own `Menu.qml`. The sibling plugins get follow-up
   issues (listed below). This task does not change them.

**How the shell scales text** (omarchy 4.0.4,
`share/omarchy/shell/Commons/Style.qml`, the `qs.Commons` that `Menu.qml:6`
imports):

- `[font] base-size` in `~/.config/omarchy/shell.toml` (default 12) is the
  root. Every `Style.font.<token>` is `round(base-size × multiplier)` unless
  the theme pins that token (`Style.qml:279-333`). `omarchy display text size
  <9-20>` sets it for the shell, GTK and terminals together, and the shell
  re-flows live.
- `Style.space(px)` scales by the same factor (`effectiveSpacingScale`,
  `Style.qml:208-221`), so the window, card and gaps grow with base-size.
- Monitor scale (Hyprland `monitor=…,scale`) is applied by the compositor.
  QML sizes are logical pixels, so text and window both follow it already.
  Correction to the intent: the 1.45 does not double the *monitor* scale. It
  stacks on the shell's *text-size* setting, and it makes the menu 45%
  larger than the shell at every size.

**Change, `Menu.qml` only:**

- Delete `textScale` and `px()` (`Menu.qml:22-23`).
- `Line` body text (`Menu.qml:52`): `Style.font.caption` × 1.45 becomes
  `Style.font.title` (base-size × 1.167).
- Card title (`Menu.qml:189`): `Style.font.subtitle` × 1.45 becomes
  `Style.font.heading` (base-size × 1.333).

| base-size | body now → new | card title now → new |
| --------- | -------------- | -------------------- |
| 12 (default) | 15 → 14 | 19 → 16 |
| 16 | 19 → 19 | 25 → 21 |
| 20 | 25 → 23 | 32 → 27 |

At the default size, body text shrinks by 1px and the card title by 3px.
That is on purpose: the menu stays two token steps above the shell's usual
`caption`/`body` text (the most-used sizes in the shell's own QML), and the
title stays clearly above the body text. If a theme pins `title` or
`heading` in `shell.toml`, the menu follows it.

Unchanged: window and card geometry (`Menu.qml:25-31, 59, 72-75`), both
`TextField`s (`Menu.qml:160, 208`), which use the shell's `qs.Ui`
`TextField` at `Style.font.body` (`Ui/TextField.qml:41`), keys, colours.

**Guard:** a flake check `no-text-multiplier` next to `no-hardcoded-colours`
(`flake.nix:93-99`). It fails if `Menu.qml` contains `textScale`, `uiScale`,
`px(` or a `pixelSize:` that is not a `Style.font.*` token.

## Alternatives rejected

- **Keep 1.45, divide by `Style.fontScale`.** Freezes text at a fixed pixel
  size, so it stops following the text-size setting. The opposite of the
  requirement.
- **`Style.fontPx(1.25)` / `Style.fontPx(1.583)`.** Keeps today's 15/19px
  exactly and is scale-aware, but `fontPx` is an internal helper, not a
  token. It skips theme pins in `shell.toml`, and the same fraction would
  have to be copied into four other repos.
- **Take a factor from the monitor (`screen.devicePixelRatio`).** The
  compositor already applies it. Multiplying again would double it.
- **A new shared `Style.font.menu` token in omarchy.** The cleanest end
  state, but it is an upstream omarchy change. The existing `title` and
  `heading` tokens do the job now. Worth raising upstream if the siblings
  agree.
- **Plain `caption`/`subtitle` (no step up).** Matches the shell, but drops
  the deliberate larger menu (decision 2) and makes long store text hard to
  read at the menu's width.

## Risks

- **Smaller at the default size.** A user used to 15/19px sees 14/16px.
  Mitigation: the table above goes into the PR, and razer is checked by eye.
- **Themes that pin `title` or `heading` very small or very large** change
  the menu too. This is intended: it follows the theme.
- **Overflow at base-size 20.** The card is `min(Style.space(1000), 70% of the
  monitor)` wide (`Menu.qml:72`). The text is no larger than today at any
  size, so wrapping gets easier, not harder. Still checked at 20.
- **Font family.** `Line` uses `Style.font.family`, not the shell's
  `menuFamily` (`OMARCHY_MENU_FONT`). Out of scope here, noted only.

## Verification

1. `nix flake check -L`: the new `no-text-multiplier` check passes, and it
   fails on a scratch copy with `textScale` put back (negative test, not
   committed).
2. `tests/model.sh` still passes. It tests `FlatsnapModel.qml`, which this
   change does not touch, so it proves nothing broke next to it.
3. QML load check: `quickshell -p` on the installed plugin layout (as
   `tests/model.sh` does) loads `Menu.qml` with no `ReferenceError` for
   `px`/`textScale`.
4. Manual on **razer only** (never p620), after a dev install of the plugin
   (staged outside `plugins/` and moved in):
   - Monitor scale 1 and monitor scale 2 (or razer's native fractional
     scale): open the menu, look up an app, open Declared. Text and window
     scale together, nothing clipped.
   - `omarchy display text size 16` and then `20`, menu open: text re-flows
     live and keeps the same size relative to the bar and other shell
     panels. Then `omarchy display text size reset`.
   - Screenshots of both states attached to the PR.
